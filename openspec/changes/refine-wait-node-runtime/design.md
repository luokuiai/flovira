## Context

当前 WAIT 任务本身只保存节点标识，恢复时通过 `definitionId + nodeCode` 查询当前 `flow_node`，再读取 `waitConfig`。流程定义允许原 ID 更新并重建节点，因此运行中实例的等待标识可能随定义编辑而改变。实例已有 `def_json` 完整定义快照，可作为稳定配置来源，无需扩展任务表。

WAIT 的外部恢复先执行 `claimWait`，但超时服务先执行通用 `claimTimeout`，再调用公开的 `resumeClaimedTask` 绕过 WAIT 抢占。两个状态都复用任务的超时状态字段，却形成两条不同的并发路径。

## Goals / Non-Goals

**Goals:**

- 已启动实例始终按启动时的 WAIT 配置恢复。
- 外部信号、超时扫描和重复请求最多只有一个推进成功。
- WAIT 与普通超时继续复用现有任务流转、监听器、网关和历史机制。
- 按实例等待标识恢复时只查询 WAIT 任务，并具有匹配查询的数据库索引。
- 不增加运行表、任务字段或额外调度基础设施。

**Non-Goals:**

- 不改变 WAIT 配置的前端模型和定义校验规则。
- 不实现消息中间件订阅、持久化事件收件箱或无限期历史事件检索。
- 不改变普通审批任务的超时快照和失败重试语义。

## Decisions

### 1. 从实例定义快照解析 WAIT 配置

`WaitServiceImpl` 加载任务所属 `Instance.defJson`，按 `nodeCode` 定位 `NodeJson`，并通过统一配置工具解析 `waitConfig`。同一次按实例恢复只解析一次快照，再匹配该实例的当前 WAIT 任务。

未选择在 `flow_task` 新增 `wait_key`，因为实例快照已经冻结了所需配置；增加字段会扩大四套数据库、三个 ORM 实体和历史模型的契约面。代价是每次恢复需要解析一份定义 JSON，但审批流程节点规模有限，且实例/标识恢复只解析一次。

### 2. WAIT 只保留一个可抢占的恢复入口

外部恢复和 `RESUME_WAIT` 超时都在事务内执行 `claimWait(taskId, now)`，成功者调用相同的私有推进逻辑；失败者返回幂等未命中结果。删除公开的 `resumeClaimedTask`，防止调用方绕过状态转换。

普通审批超时仍使用 `claimTimeout`、失败释放和过期 claim 恢复。WAIT 超时不预先调用通用 claim，避免两个原子状态转换之间出现中间态。

### 3. 系统节点通过专用服务入口推进

`TaskService` 增加系统任务推进方法，集中设置跳过权限、委派和会签检查所需的内部标志，再委托现有 `skip` 管线。WAIT 和普通超时只负责提供动作、处理人、消息、历史扩展和变量。

该入口不复制任务完成逻辑，因而继续保留现有监听器、变量、网关、历史任务和后续节点行为。

### 4. 增加实例 WAIT 任务的定向查询

`TaskService`/`FlowTaskDao` 增加按 `instanceId + nodeType` 查询方法，并在三个 ORM 实现中对齐。四种数据库的 `flow_task` 增加 `(tenant_id, instance_id, node_type)` 组合索引，以适配多租户过滤和实例 WAIT 查询。

索引只加入当前完整初始化脚本；本 fork 从 1.0.0 起版，不生成历史升级脚本。

## Risks / Trade-offs

- [实例快照损坏或缺少节点] -> 明确抛出配置异常并保持事务回滚，不回退读取当前定义，以免静默改变实例语义。
- [定义 JSON 解析有固定开销] -> 单次实例恢复只解析一次，并先通过定向查询缩小任务集合。
- [WAIT 超时失败后的重试] -> WAIT claim 与推进在同一事务，推进异常会回滚 claim，下一轮扫描仍可重试。
- [删除公共绕过方法造成源码不兼容] -> 当前 fork 从 1.0.0 重新发布，不保留不安全的过渡 API。

## Migration Plan

1. 同版本发布 core、三个 ORM 适配和四套初始化 SQL。
2. 新部署直接执行对应数据库的完整初始化脚本。
3. 已自行建库的试用环境需手工补同名组合索引；不需要数据回填。
4. 回滚代码时可保留新增索引，索引不改变数据语义。
